---
title: Zero-knowledge
description: Exactly how NoteKit is built so the server never knows your keys — and therefore never knows your data.
---

The strongest claim NoteKit makes is also the simplest: **we cannot read your notes, and we cannot
read your keys.** This page explains precisely how the architecture enforces that, so you don't have
to take it on faith.

The guarantee rests on one fact: **the keys that decrypt your data are generated on your device and
never leave it.** Everything else follows.

## Your keys are born on your device

There is no "create account → server generates your key" step. When you first unlock a vault, the key
material is derived or generated **locally**:

- Your **identity keys** come from a 24-word BIP39 phrase (or a wallet signature) that is turned into a
  seed *on your device*. The server never sees the phrase, the seed, or the private keys derived from
  it. See [key hierarchy](/reference/cryptography).
- Each **device** additionally generates its own random age + Ed25519 keypair, locally, on first run.

The server is never a party to any of this. It has no key-generation endpoint, no key-escrow table, no
"recovery" that involves us — because we have nothing to recover from.

## Private keys never travel

Across every surface, the private half of every key stays put:

| Surface | Where the private key lives | Leaves the device? |
| --- | --- | --- |
| Web / Mobile | IndexedDB (in the browser/WebView) | Never |
| Desktop | OS keychain | Never |
| CLI | OS keychain (or `NOTEKIT_TOKEN` env for headless) | Never |
| MCP | local file, mode `0600` | Never |

What *does* get published to the vault is only the **public** half — your public recipients (`age1…`)
and public signing keys, in the device roster. Public keys can encrypt *to* you and verify your
signatures; they cannot decrypt or impersonate.

## Encryption happens before the network

Because the crypto lives in the shared core, **every** surface encrypts on the device before a single
byte is sent (see the [data flow](/how-it-works/data-flow)). By the time content reaches the transport,
it is already an armored `age` blob. The API and the Git host receive ciphertext and store ciphertext.

## What the server actually holds

<SystemArchitectureDiagram />

The backend (`apps/api`) is a **relay**. It authenticates you, checks that you may access a vault, and
passes encrypted bytes to and from the Git provider. It binds a Postgres database (accounts, vault
references, device rosters of **public** keys, quotas) and a Git host (Forgejo/GitHub/GitLab) that
stores the repository. In neither place is there a key that can decrypt your content.

It can see **metadata** — folder names, timestamps, ticket status, file sizes, commit authors, and who
a note is shared with. It cannot see titles, bodies, tags, URLs, or secret values. The full list is in
the [threat model](/how-it-works/threat-model).

## Why you don't have to trust us on this

Three properties make the guarantee checkable rather than promised:

1. **Open source.** The clients are open; you can read the exact code that generates keys and encrypts
   content, and confirm no key material is sent to the server.
2. **It's plain `age` and Git.** Your vault is a Git repository of standard `age`-encrypted files.
   Clone it with any Git client and you'll find ciphertext — the same thing we store. No NoteKit-specific
   server is required to hold or inspect your data.
3. **Signed, verifiable trust.** New devices and shared recipients are admitted through a signed device
   roster rooted in *your* key, and verified client-side. A malicious server can't inject a key it
   controls to start reading new writes — the unsigned entry is rejected before it's ever used. See
   [devices & pairing](/how-it-works/devices-and-trust).

## The honest edges

Zero-knowledge is about the **server**. It does not mean magic:

- A device that already holds your keys can read what that device can read — protect your devices.
- Metadata (above) is visible to the host by design, so the app can work offline.
- Revocation is **forward-only**: it stops future access, it cannot un-send already-shared history
  (that's a property of Git, and we don't pretend otherwise). See
  [sharing & revocation](/how-it-works/sharing-and-revocation).

That's the whole deal: keys made on your device, kept on your device, used on your device — and a
server that only ever moves ciphertext around.
