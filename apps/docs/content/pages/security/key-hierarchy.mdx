title: Key hierarchy

Your entire vault hangs off one **seed**. The seed comes from either a 24-word recovery phrase or an
EVM wallet signature; both produce the same shape of seed and derive the same two identity keys.

<KeyHierarchyDiagram />

## Seed source 1 — the 24-word recovery phrase

When you first sign in, NoteKit generates a **BIP39 mnemonic**:

- **24 words = 256 bits of entropy**, from the BIP39 English wordlist.
- The phrase is stretched to a **64-byte seed** with `mnemonicToSeed`, using a fixed,
  application-versioned BIP39 passphrase (`notekit-recovery-v1`).

This phrase is the master key to your vault. NoteKit never sees it and cannot recover it for you.

## Seed source 2 — an EVM wallet signature

Web3 users can unlock with a wallet instead. The wallet signs a fixed, domain-separated message with
`personal_sign` (EIP-191); the signature is deterministic (RFC 6979). NoteKit stretches it into the
same 64-byte seed with **HKDF-SHA256**:

```text
seed = HKDF-SHA256(
  ikm  = wallet_signature,
  salt = "",                          // the signature is already high-entropy
  info = "notekit-wallet-seed-v1",
  len  = 64 bytes
)
```

The signature never leaves your device and is not a transaction.

## Deriving the two identity keys

From the 64-byte seed, NoteKit derives two independent keys with **domain separation** so they can
never be confused for one another:

**Age encryption identity (X25519)** — decrypts your vault key:

```text
scalar   = seed[0:32]
identity = bech32("AGE-SECRET-KEY-", scalar)   // an age secret key
recipient = identityToRecipient(identity)      // the public "age1…" address
```

**Signing key (Ed25519)** — the root of trust that authorizes devices:

```text
privateKey = SHA-512("notekit-recovery-sign-v1" ‖ seed)[0:32]
publicKey  = ed25519.getPublicKey(privateKey)
```

The signing public key is published in `.notekit/recovery.json`; the private signing key stays cold —
it only ever signs the very first ("genesis") device roster. Day-to-day, your devices sign for each
other (see [Devices & pairing](/security/devices-and-pairing)).

<Callout>
Same phrase (or same wallet) → same seed → same identity, on every device and forever. That
determinism is what makes recovery possible without the server holding anything.
</Callout>

## Per-device keys

Each device (browser install, desktop, mobile, CLI, MCP server) also generates its **own** random
keys, which never leave that device:

- a **device age key** (random X25519) — added as a recipient of the vault key, so the device can
  decrypt content;
- a **device signing key** (random Ed25519) — signs roster and keybox updates so the master signing
  key can stay cold.

Private keys are stored locally only: IndexedDB (`notekit-crypto` DB) in browsers, the OS keychain for
the CLI, a config file for the MCP server. They are never written into the vault.

## Where each key lives

| Key | Type | Derived / random | Stored | Published? |
| --- | --- | --- | --- | --- |
| Recovery identity | X25519 | from seed | in your head (phrase) | public recipient only |
| Recovery signing key | Ed25519 | from seed | in your head (phrase) | public key in `recovery.json` |
| Device age key | X25519 | random per device | local key store | public recipient in roster |
| Device signing key | Ed25519 | random per device | local key store | public key in roster |
| Vault key | X25519 | random per vault | wrapped in `keybox.age` | never (sealed) |
